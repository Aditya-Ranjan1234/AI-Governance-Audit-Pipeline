Connect private PostgreSQL data to Tableau

A repeatable procedure for reaching the AI Governance database through a secure Kubernetes tunnel, connecting Tableau, and building four dashboard views without relationship errors.

AWS region: us-west-2 Database: governance No public RDS exposure Tableau on Mac
How the connection works

Keep PostgreSQL private

The RDS database is inside private AWS subnets. The Mac reaches it through the existing EKS cluster instead of opening PostgreSQL to the internet.

Your MacAWS CLI, kubectl and Tableau are installed locally.
→
Kubernetes tunnelA temporary forwarding pod runs inside the governance namespace.
→
Amazon RDSPrivate PostgreSQL database stores events, findings and dashboard views.
→
TableauConnects to localhost port 15432 as if PostgreSQL were local.
Why localhost works

kubectl port-forward carries database traffic through the authenticated EKS API. Tableau connects to 127.0.0.1:15432; the temporary pod forwards that traffic to private RDS.

Connection procedure

Start the secure database tunnel

Run these steps in Terminal. The forwarding session remains active only while the final command is running.

1

Create the temporary forwarding pod

This pod has no database password. It only forwards network traffic from EKS to the private RDS endpoint.

kubectl -n governance run tableau-rds-tunnel \
  --image=alpine/socat \
  --restart=Never \
  -- TCP-LISTEN:5432,fork,reuseaddr \
  TCP:ai-governance-postgres.c1eyg8c0m39g.us-west-2.rds.amazonaws.com:5432
2

Wait until the pod is ready

kubectl -n governance wait \
  --for=condition=Ready pod/tableau-rds-tunnel \
  --timeout=90s

Expected result: pod/tableau-rds-tunnel condition met.

3

Forward a local Mac port

kubectl -n governance port-forward \
  pod/tableau-rds-tunnel 15432:5432
Keep this Terminal window open

Closing it stops the tunnel. Tableau will then report that the database connection was lost.

4

Retrieve the AWS-managed database password

Run this in a second Terminal window. Copy the displayed password directly into Tableau. Do not save it in the HTML guide or share it in messages.

SECRET_ARN=$(aws rds describe-db-instances \
  --db-instance-identifier ai-governance-postgres \
  --region us-west-2 \
  --query 'DBInstances[0].MasterUserSecret.SecretArn' \
  --output text)

aws secretsmanager get-secret-value \
  --secret-id "$SECRET_ARN" \
  --region us-west-2 \
  --query SecretString \
  --output text |
python3 -c 'import json,sys; print(json.load(sys.stdin)["password"])'

Prevent relationship mismatch

Create four separate data sources

Do not drag all four database views onto one relationship canvas. Each view has a different level of detail. Create one Tableau data source and one worksheet for each view, then combine the worksheets in a dashboard.

Data source 1

tableau_framework_status

One row per day and framework. Use for framework finding counts, critical counts and average risk.

Data source 2

tableau_risk_trend

One row per five-minute bucket, producer and rule. Use for baseline versus Isolation Forest risk trends.

Data source 3

tableau_incident_history

One row per individual finding. Use for the incident table, severity, evidence and model status.

Data source 4

tableau_pipeline_latency

One row per five-minute bucket and producer. Use for p50, p95 and p99 end-to-end latency.

Why Tableau showed “relationship mismatch”

The views do not share one consistent key. Framework Status is aggregated by day and framework, Risk Trend by time bucket, producer and rule, Incident History by finding ID, and Pipeline Latency by time bucket and producer. Joining them can duplicate findings and distort totals.

A

Add each view correctly

  1. Connect to PostgreSQL and drag only tableau_framework_status onto the canvas.
  2. Open Data → New Data Source.
  3. Reconnect using the same localhost settings and add only tableau_risk_trend.
  4. Repeat for Incident History and Pipeline Latency.
  5. Create one worksheet from each data source.

Free Tableau account

If your app is Tableau Public

Tableau Public does not keep a private live PostgreSQL connection. Export each dashboard view to a CSV extract, then connect each CSV as a separate Tableau data source.

Published Tableau Public data is public

Use only synthetic or sanitized demonstration records. Do not publish real user identities, prompt contents, evidence payloads, credentials or confidential compliance findings.

1

Keep the tunnel running

The export tool still needs the same localhost tunnel described above.

2

Export the four views

Use a PostgreSQL client such as psql to export each view with a header row. Store the files in a dedicated local folder.

mkdir -p "$HOME/Downloads/tableau-governance"

SECRET_ARN=$(aws rds describe-db-instances \
  --db-instance-identifier ai-governance-postgres \
  --region us-west-2 \
  --query 'DBInstances[0].MasterUserSecret.SecretArn' \
  --output text)

DB_PASSWORD=$(aws secretsmanager get-secret-value \
  --secret-id "$SECRET_ARN" \
  --region us-west-2 \
  --query SecretString \
  --output text |
python3 -c 'import json,sys; print(json.load(sys.stdin)["password"])')

PGPASSWORD="$DB_PASSWORD" psql -h 127.0.0.1 -p 15432 \
  -U governance_admin -d governance \
  -c "\copy tableau_framework_status TO '$HOME/Downloads/tableau-governance/framework-status.csv' CSV HEADER"

PGPASSWORD="$DB_PASSWORD" psql -h 127.0.0.1 -p 15432 \
  -U governance_admin -d governance \
  -c "\copy tableau_risk_trend TO '$HOME/Downloads/tableau-governance/risk-trend.csv' CSV HEADER"

PGPASSWORD="$DB_PASSWORD" psql -h 127.0.0.1 -p 15432 \
  -U governance_admin -d governance \
  -c "\copy tableau_incident_history TO '$HOME/Downloads/tableau-governance/incident-history.csv' CSV HEADER"

PGPASSWORD="$DB_PASSWORD" psql -h 127.0.0.1 -p 15432 \
  -U governance_admin -d governance \
  -c "\copy tableau_pipeline_latency TO '$HOME/Downloads/tableau-governance/pipeline-latency.csv' CSV HEADER"

unset DB_PASSWORD
3

Open the CSVs separately

In Tableau Public, select Connect → Text File. Add one CSV, create its worksheet, then use Data → New Data Source for the next CSV. Combine the four worksheets in a dashboard.

After using Tableau

Close and remove the tunnel

Stop the port-forward command with Control+C, then delete the temporary forwarding pod.

kubectl -n governance delete pod tableau-rds-tunnel
The database remains available to the pipeline

Deleting the tunnel pod only removes access from the Mac. It does not delete PostgreSQL, dashboard views, findings or any governance service.

Troubleshooting

Common connection problems

Work from the tunnel outward: AWS identity, EKS access, forwarding pod, local port, then Tableau.

Tableau says it cannot connect to PostgreSQL

Confirm the Terminal window still shows Forwarding from 127.0.0.1:15432. If it was closed, run the port-forward command again. Also confirm Tableau uses server 127.0.0.1 and port 15432.

The tunnel pod already exists

Reuse it if it is Running, or delete it and recreate it:

kubectl -n governance get pod tableau-rds-tunnel
kubectl -n governance delete pod tableau-rds-tunnel
kubectl reports an authorization or timeout error

Refresh the EKS configuration and retry:

aws eks update-kubeconfig --name ai-governance-eks --region us-west-2
kubectl get nodes

If the public IP of the Mac changed, the EKS API allowlist may also need to be updated.

Tableau shows a relationship mismatch

Remove the additional views from the current relationship canvas. Create a new Tableau data source for each view. Combine their worksheets in a dashboard instead of joining the views.

No tables or views appear

Confirm the database is governance and search for view names beginning with tableau_. The four expected views are listed in the Data Sources section above.
